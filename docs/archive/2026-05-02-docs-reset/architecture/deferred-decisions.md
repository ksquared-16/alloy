# Deferred decisions & future considerations

Items **intentionally not solved** in current foundation doctrine. Prevents silent scope creep and preserves explicit triggers for reopening.

| Topic | Description | Why deferred | Doctrine assumes for now | Likely trigger to revisit |
|-------|-------------|--------------|----------------------------|---------------------------|
| **Multi-payer / split financial responsibility** | Multiple parties sharing invoice, deposits, or guarantor vs occupant payment rules beyond simple single-payer flows. | Requires billing domain model, allocation rules, and UI complexity not needed for first resolver/work-unit foundation. | Single logical **financial context** on a record; complex splits handled manually or outside v1 payload contract. | Recurring multi-invoice splits, formal AR sub-ledger, or regulated markets requiring documented payer roles. |
| **AI-driven layout from telemetry** | ML/AI proposing overview bands, queue ordering, or work-unit grouping from usage data. | Acknowledged in [workspace doctrine](./workspace-work-unit-scope-doctrine.md#future-ai-compatibility-not-implementation-now); no product requirement to ship inference. | **Human-approved config** only; templates stay fixed; AI suggestions are non-authoritative if ever added. | Stable telemetry pipeline + explicit governance for auto-applied vs suggested config. |
| **Full capability / ABAC model** | Capabilities + policies beyond coarse `user_roles` and RLS patterns. | Incremental **scope** storage is not designed yet; full ABAC is easy to overbuild wrong. | **Role + org** (today) + documented intent to add **scope + capability** later (see glossary). | Need for field-level or record-level denial separate from org membership; compliance-driven segregation of duty. |
| **Billing account abstraction** | Dedicated “billing account” entity decoupled from customer or job for enterprise AR. | No evidence yet that customer/job/container split is insufficient for near-term industries. | **Customer** and operational records carry financial context; GL/payment tables as today. | Multi-customer consolidated billing, formal sub-accounts, or third-party payer hierarchies. |
| **Vendor ↔ person symmetry** | First-class **`vendor_persons`** (or equivalent) mirroring **`customer_persons`**. | Vendors still **contact-linked** in schema; migration cost without blocking persons-first on customer side. | Continue **vendor_contacts** / **primary_contact_id**; evolve when customer path is stable. | New product surfaces that require vendor staffing, compliance, or directory parity with customer persons. |
| **Multi–work-unit membership per record** | Same operational record in multiple work units simultaneously (M2M). | Single **`jobs.work_unit_id`** is enough for first routing; M2M adds join tables and UI ambiguity. | **One primary work unit** on job unless/until join table exists; handoffs modeled in process, not data, until needed. | Cross-functional queues that must show the same job in two units without duplication or proxy records. |
| **Strict DB enforcement: job org vs work unit org** | Trigger/check that **`jobs.org_id`** matches **`work_units.org_id`** when `work_unit_id` set. | Documented gap; app-layer validation has carried the load. | Service routes must validate consistency; foundation may add DB guard. | Recurring bad data from integrations or parallel clients bypassing app checks. |
| **Universal `queue_definition` DSL** | Versioned JSON language for all queue filters across entities. | Empty `{}` today; premature standardization risks wrong abstraction. | Per-work-unit JSON with **documented v1 subset** when foundation ships (see foundation plan). | Second vertical needs incompatible filters or shared queue engine across entities. |
| **Contacts table removal** | Dropping **`contacts`** or stopping dual-write. | High blast radius on booking, admin, messaging. | **Persons canonical** for new design; **contacts** compatibility path until phased migration completes. | Majority of reads/writes on persons/customer_persons + safe backfill story. |
| **Employee / staff as persons + app users** | Linking operational staff records to auth for field apps. | No dedicated employee table pattern locked; overlaps scope/capability work. | Admins via **`user_roles`**; field identity out of scope for Track A unless explicitly pulled in. | Mobile/technician apps need roster, scheduling attribution, or per-tech scopes. |
