# KPI Configuration v0 Sprint

Objective:
Make workspace KPIs configurable across org, department, and work-unit surfaces without breaking performance, queue accuracy, or the config-driven foundation.

Why now:
The workspace shell is stable: shared layout, sticky rail, exact queue counts, config-selected queue preview templates, and compact KPI/scorecard presentation. The next step is allowing operators/admins to decide which registered metrics appear, in what order, and on which surface.

Important doctrine:
- Config chooses which registered KPI appears.
- Code owns metric definitions and calculation logic.
- Do not allow arbitrary SQL or unvalidated calculation logic in config.
- Preserve performance and existing contracts.

--- 0.E How each KPI is computed (classification) ---

Legend: SV = server-returned numeric/value in API JSON; CV = client-only math/formatting; Q = queue summary
        count; L = lifecycle endpoint aggregation over opportunity rows + status definitions.

| Location / metric (representative) | Class |
| Org "Departments" | CV: local array length after filter |
| Org "Work units" | CV: length of work-units API items (null → "—" until loaded) |
| Org growth "Active pipeline" / "Closed outcomes" | CV sum of L-derived per-dept counts |
| Org growth "Pipeline value" | CV sum of L-derived openPipeline values; currency format client |
| AdminV2 dept strip per work unit | CV sum of Q per work unit |
| AdminV2 dept "Needs attention" aggregate | CV sum of Q for queue key needs_attention (per WU) |
| Classic KpiBlock lifecycle cells | SV counts/values from L in runtime; enrollment buckets CV-sum rows of statusBreakdown |
| Work-unit queueModel strip | No KPIVm (empty) |
| Work-unit legacy "In queue" | SV oq.total from legacy API |
| Work-unit legacy "Queue value" / "Oldest" / "Needs action" | CV over items in oq (partial list vs total documented in API) |
| Jobs adapter "Rows shown" / cap | CV from rows in memory |
| KPIBand (Admin shell) | Mock data (non-live) |

Lifecycle route semantics: L uses same effective lifecycle stage resolution as presentation (computeOpportunityLifecycleKpis +
resolveEffectiveOpportunityLifecycleStage). Row cap 5000 on the filtered query — totals can truncate if more rows match.

--- 0.F Performance risks ---

Over-fetching
   • opportunity-lifecycle-kpis loads all matching rows (max 5000) per department for KPI computation.
   • Org workspace fires one lifecycle GET per growth-slice department in parallel (N departments, not N arbitrary metrics).
   • useOperationsWorkspaceData for growth/enrollment fetches multiple legacy queue endpoints plus lifecycle KPI in parallel.

Duplicated aggregation
   • Lifecycle KPI computation and queue exact counts both touch opportunities with filters derived from definitions;
     no shared in-process cache between lifecycle route and QueueService across HTTP requests.
   • Department adminV2 page: work-unit-queue-summaries batches all WUs; separate from lifecycle-kpis (different product numbers).

N+1 risk
   • Org page: N_lifecycle = number of growth/enrollment departments — bounded by org dept list, parallel.
   • Classic hook: N_queue = fixed key list (7 queue fetches) + 1 lifecycle — parallel, not per-metric arbitrary N.

Repeated client computation
   • useMemo on kpis in shells/pages; KPIBlock useMemo for strip merge — low cost.
   • Work-unit queueModel recomputes large vm item mapping when queue items change — not KPI-specific but hot path.

Queue / KPI drift risk
   • Lifecycle KPI scope = pipeline_overview definition when present; department strip sums per-WU queue totals — same
     underlying entities can differ if definitions or work_unit scoping diverge.
   • needs_attention queue summary with include_previews=false uses fetch cap 800 in QueueService — can under-count vs full set;
     lifecycle unscoped rows can disagree with queue totals.
   • Work-unit primary path: KPI strip empty but badges use QueueService — operators see counts only in tabs, not the same
     cells as legacy path KPIs.

--- 0.I Reusable vs fragile ---

Reusable
   • KPIVm as stable presentation DTO; KPIBlock merge/slice behavior.
   • computeOpportunityLifecycleKpis as single place for lifecycle math.
   • QueueService as single place for exact queue counts and preview assembly.
   • workspaceRootRollup org aggregation pattern (growth-slice gated).

Fragile
   • Two department experiences (adminV2 bridge strip vs classic KpiBlock) with different numbers and labels.
   • Work-unit KPI strip absent on QueueService path (`kpis: []`) vs populated legacy path — behavioral split.
   • buildEnrollmentDepartmentKpis unused — risk of drift if reintroduced without aligning to KpiBlock/lifecycle.
   • Reliance on magic work_unit keys (pipeline_overview, needs_attention, enrollment_pipeline) for labels and scope.

--- 0.J High-level recommended direction only (post-audit) ---

   • Treat "registered metrics" as explicit keys with one server-side snapshot per scope; map to KPIVm in one layer so
     adminV2 dept strip, classic KpiBlock, and work-unit surfaces can share definitions where product intends parity.
   • Resolve growth vs ops vs queue-only metrics in the catalog to avoid comparing lifecycle totals to per-WU queue sums
     without documenting semantics.
   • When adding config, prefer reusing existing batched payloads (dept batch summaries, lifecycle response) over per-KPI
     queries; preserve QueueService contracts.

--- 0.5.1 KPI source of truth (LOCKED: layered model) ---

**Decision:** Use a **layered** model — there is **no** single numeric source for all KPIs. Each **registered**
metric (in code) declares which **computation family** it uses; config only selects among registered keys.

**Computation families for v0 (code-defined, not configurable):**
- **L — Lifecycle aggregate:** `GET …/opportunity-lifecycle-kpis` payload + `computeOpportunityLifecycleKpis`
  semantics (scoped per route; pipeline_overview definition when present; row cap as today).
- **Q — Queue summary aggregate:** QueueService outputs — `GET …/work-unit-queue-summaries` and/or
  `GET …/work-units/:id/queues` (same params family as the UI that shows the badge/tab).
- **S — Structure counts:** Department list / work-unit list lengths (org structure strip).
- **R — Rollup helper:** Client aggregation already used at org (e.g. sum of L across growth-slice depts).

**Authoritative source by route (which number wins when product asks “what is truth?”):**

- `/adminV2/workspace` (org) — Departments & work units: **S**
- `/adminV2/workspace` (org) — Growth pipeline strip (active pipeline, pipeline value, closed outcomes): **L**, then **R** for org row
- `/adminV2/workspace/dept/[departmentId]` — Per–work-unit totals in compact strip: **Q** (batched `work-unit-queue-summaries`; sum of queue `count` per WU as today)
- `/adminV2/workspace/dept/…/work-unit/[workUnitId]` — Tab / badge / list totals for selected queue: **Q** (QueueService path); legacy queue APIs only where QueueService is not used
- `/admin/workspace/dept/…` (classic) — `KpiBlock` opportunity lifecycle pipeline: **L** via `runtime.opportunityLifecycleKpis`

**Explicit non-goals for v0:** Forcing numeric equality between **L** totals and **Q** row sums across arbitrary
queue keys without a registry-defined relationship.

--- 0.5.2 Drift rules (LOCKED) ---

1) **Queue-parity rule**  
   Any metric registered as **queue-backed** (family **Q**) MUST be computed from the **same HTTP response
   and parameter profile** that feeds the queue UI for that scope (e.g. same `count_mode`, `include_previews`,
   `summary_mode`, work unit id). Producers MUST NOT re-derive that number from a second fetch with different
   query params.

2) **Lifecycle-parity rule**  
   Any metric registered as **lifecycle-backed** (family **L**) MUST use the lifecycle endpoint + row cap /
   scope documented in the **metric registry** (not in DB config). UI copy MUST NOT imply equality with a
   queue-tab count unless a single registry entry explicitly documents that relationship.

3) **needs_attention and caps**  
   When QueueService applies a **bounded load** for count-only paths (e.g. needs_attention cap in Card 0 audit),
   **queue-backed** KPIs MUST match the **same** count the **queue tab / badge** shows (including cap behavior).
   **Locked:** Prefer **honest parity with the tab** over inventing a second uncapped KPI in v0 without a new
   server aggregate. If product later requires uncapped exact counts, that is a **new metric + API**, not config
   formula work.

4) **Cross-family comparison**  
   Operators may see **L** numbers on org workspace and **Q** numbers on dept strip; training/docs treat them
   as different lenses unless a future registry links them.

--- 0.5.4 Performance posture (LOCKED for v0) ---

**N+1 / batching:**
- At most **one** batched dept queue summary request per adminV2 dept page load for Q-family dept strip (today's pattern).
- At most **one** lifecycle GET per growth-slice department invoked on org load (today's parallel pattern) —
  not one HTTP call per KPI.
- Work-unit: reuse **existing** queue summary + items fetch boundaries; **no** additional per-metric GET in v0.

**Client computation:**
- Avoid multiple full passes over large opportunity arrays for KPI formatting; slice/map **once per payload**
  in the producer layer (Card 1 will name modules).

**Large row fetches:**
- Lifecycle **5000-row cap** and existing QueueService query patterns remain **baseline** for v0; eliminating
  them is **not** a KPI-config deliverable (separate performance work).

**Endpoints vs shared service:**
- **v0 MAY reuse current endpoints only** behind registry resolvers/adapters, as long as batching rules above hold.
- A **shared server “KPI snapshot” layer** is **optional** in Card 1 design — not a prerequisite to ship v0,
  provided duplication of aggregates stays within acceptable latency (Card 1.5 may still choose a snapshot API).

--- 0.5.5 Config boundary (LOCKED doctrine) ---

- **Config chooses** which registered KPI appears, order, visibility, labels/overrides, display hints, and
  allowed surfaces/scopes **within the registry**.
- **Code owns** metric definitions, computation family (**L** / **Q** / **S** / **R**), filters, joins,
  aggregation, and all math.
- **No arbitrary SQL** from config; no user-supplied query fragments.
- **No dynamic formulas** in config (no spreadsheet expressions, no eval).

--- 1.0 Architecture goal (one sentence) ---

Org-defined **placement** (which registered metrics appear, in what order, with what labels/lanes) lives in
**config**; **computation** is entirely **code** via a **single resolution pipeline** that reads **at most
one batch per family per page transition** (L / Q / S / R), then maps results into `KPIVm[]` for KPIBlock or
filtered layout for KpiBlock — **no per-metric network calls** and **no config formulas**.

================================================================================
1. KPI REGISTRY DESIGN (core)
================================================================================

--- 1.1 What the registry is ---

The **KPI Registry** is a **code-first catalog** (TypeScript module or generated const object in v0). It is the
**only** place that defines:
- `metric_key` — stable string identifier (e.g. `org.structure.departments_count`). **Card 1.5** freezes the v0 enum.
- `family` — one of **L | Q | S | R** (per Card 0.5). **Never** stored in DB config.
- **Resolver binding** — which **batch payload** and which **pure function** extract a display value.
- **Allowed surfaces** — subset of `workspace | department | work_unit`.
- **Scope needs** — what runtime context is required (org only, department_id, work_unit_id, growth-slice only, etc.).

Database **config** rows reference **`metric_key` only**; unknown keys are **skipped** with a logged warning
(**Card 1.5**: strict fail vs skip).

--- 1.2 Registry entry shape (conceptual; not a DB table) ---

Each entry conceptually contains:

  metric_key          stable string (namespaced e.g. org.*, dept.*, wu.*)
  family              L | Q | S | R
  default_label       string
  default_format      count | currency | percent | duration | text  (maps to formatting helpers)
  default_lane        business | ai                         (KPIVm.lane)
  allowed_surfaces    which of workspace / department / work_unit
  scope_rules         org_required, growth_slice_only?, facet?, etc.
  binding             family-specific (see 1.3)
  parity_note         plain text: L vs Q semantics for operators

**No** formula, sql, or expression fields. **No** user-defined JSON paths in config — field pickers are fixed per key in code.

--- 1.3 Mapping families to data sources (no arbitrary formulas) ---

**L (Lifecycle)**
- **Batch payload:** JSON from `GET /api/admin/departments/:departmentId/opportunity-lifecycle-kpis` (existing).
- **Binding:** Each L-metric names a **single** extractor implemented in code: e.g. `counts.intake`,
  `values.openPipeline`, a named rollup over `statusBreakdown` (same semantics as today’s KpiBlock buckets,
  encapsulated in one function per metric key — not configurable logic).

**Q (Queue summary)**
- **Batch payloads:** Dept → `GET …/work-unit-queue-summaries` (same params as queue cards). Work-unit →
  `GET …/work-units/:id/queues` summary array already loaded for tabs.
- **Binding:** Small **enumerated** set of reducers in code, e.g. `sum_queue_counts`, `count_by_queue_key`,
  `selected_tab_total` (context = selected queue key from UI). Reducers read **only** summary `count` fields —
  no second scan of full item lists for counts.

**S (Structure)**
- **Batch payload:** Results of existing department list + work-units list calls (org page).
- **Binding:** Fixed extractors: e.g. `active_departments.length`, `work_units.items.length`.

**R (Org rollup)**
- **Batch payload:** **Not** a separate HTTP family — output of **multiple L batches** (one per growth-slice dept)
  already fetched for org workspace.
- **Binding:** Fixed reducers in code (e.g. sum numeric child metrics). Registry declares **dependencies** on other
  `metric_key`s (L outputs); resolver runs **L first**, then **R** in topological order.

**Prohibition:** Config cannot blend L and Q in one metric. A “blended” number requires a **new** `metric_key` and
**new** code-defined extractor with explicit semantics.

--- 1.4 Example registry keys (illustrative; enum locked in Card 1.5) ---

  org.structure.departments_count
  org.structure.work_units_count
  org.pipeline.active_in_motion    (R over L per growth dept)
  org.pipeline.pipeline_value
  org.pipeline.closed_outcomes
  dept.wu_queue.total_by_work_unit (facet: dynamic cells from one Q batch)
  wu.queue.active_tab_total        (Q + UI context)

2. KPI PLACEMENT MODEL
================================================================================

**Surfaces**

- `workspace`  →  /adminV2/workspace  →  KPIBlock
- `department` →  /adminV2/workspace/dept/[id]  →  KPIBlock
- `work_unit`  →  /adminV2/workspace/dept/…/work-unit/[id]  →  KPIBlock when strip populated

Classic `/admin/workspace/dept/…` uses **KpiBlock**; placement there is a **parallel** config stream
(visibility/order of existing lifecycle cells) if included in v0 — **Card 1.5** yes/no.

**Placement row (conceptual; DB details → Card 1.5)**

- org_id (required)
- surface — workspace | department | work_unit
- department_id — null for org-wide; set for department-scoped rows
- work_unit_id — optional override
- metric_key — validated against registry
- display_order — sort ascending
- is_visible
- label_override, format_override, lane_override (optional)
- group_key — optional; reserved (v0 may ignore)
- max_visible_strip — optional strip-level cap (**Card 1.5**)

**Validation:** `surface=workspace` with non-null department_id or work_unit_id → **reject** (aligned with Card 0.5).

**Scope precedence:** Finer scope wins for the same logical placement: **work_unit** row overrides **department** row
overrides **org workspace** defaults (same `metric_key` / surface family). **Card 1.5** encodes this in DB
constraints and seed templates.

**How many KPIs**

- KPIBlock hard cap (e.g. 5 visible) applies **after** resolver output + `mergeKpisForOrientationStrip`.
- Config may define more rows; overflow hidden by cap.
- Department facet `total_by_work_unit` may emit **N** cells (one per WU) — **Card 1.5** decides WU sort,
  whether to cap N, or paginate (product).

**Ordering / grouping**

1. Load visible rows for scope; sort by `display_order`, tie-break `metric_key`.
2. Resolve to `KPIVm[]` (§3).
3. KPIBlock: business lane first, ai lane last, then `maxVisible` slice.
4. `group_key` — no mandated UI in v0; lane is the only grouping.

================================================================================
3. RESOLUTION LAYER (critical)
================================================================================

**Single entrypoint (conceptual API)**

  resolveKpisForSurface(input) → { items: KPIVm[]; warnings: string[] }

**Input handles**

- surface, orgId, optional departmentId, workUnitId, growth flags
- **S_batch** — departments + work units list results
- **L_map** — Map<deptId, LifecyclePayload> (filled with ≤1 GET per dept)
- **Q_batch** — dept `work-unit-queue-summaries` **or** work-unit `queues` summary array
- Optional UI context: selected queue key, work unit names for labels

**Algorithm**

1. **Load placement** from config; if none → return **baseline** `KPIVm[]` matching today’s hard-coded sets.
2. **Validate** each `metric_key` against registry; unknown → skip + warning (**Card 1.5**: strictness).
3. **Ensure batches:** fetch **at most one** L response per distinct dept needed; **one** Q dept batch per dept page;
   **one** Q work-unit context per work-unit page — **never** per metric.
4. **Extract L metrics** in **one pass** per dept payload (index statusBreakdown once if multiple L keys need it).
5. **Build Q index** once: `Map<workUnitId, queues[]>` from Q batch.
6. **Compute R** after L children satisfied (dependency order).
7. **Facet expansion:** keys like `dept.wu_queue.total_by_work_unit` expand to **N** KPIVm in resolver (**one** Q batch).
8. **Format** → string values and KPIVm `id` (stable: metric_key or metric_key + wuId for facets).
9. Return ordered list for KPIBlock.

**No scattered logic:** Pages call the resolver (or a hook wrapping it); they do not hand-roll sums per metric.

4. API STRATEGY (design only)
================================================================================

**Option A — Client adapter-only (recommended default for v0)**

- Existing `fetch()` calls **unchanged** (per user constraint: no endpoint changes in this phase).
- After batches settle, client invokes `resolveKpisForSurface`.
- **Pros:** Matches Card 0.5 reuse of endpoints; no N+1.
- **Cons:** Logic lives in client until server needs it.

**Option B — Thin server KPI context endpoint (future)**

- Single route that internally invokes QueueService + lifecycle once each, returns minimal JSON for resolution.
- **Card 1.5** decides if v0 implementation uses B; design allows it without changing QueueService contracts.

**Option C — Embed kpi_context in existing responses**

- **Not recommended:** payload coupling and creep.

**N+1 guard (all options):** ≤1 L GET per covered dept per page load; ≤1 dept Q batch; work-unit Q aligned with existing bootstrap.

- Workspace org-level: unique `(org_id, metric_key)` where `surface = 'workspace'` and null scope and **active = true**
- Department: unique `(org_id, department_id, metric_key)` where `surface = 'department'` and `work_unit_id IS NULL`
  and active
- Work-unit override: unique `(org_id, work_unit_id, metric_key)` where `surface = 'work_unit'` and active

**Facet rule:** `dept.wu_queue.total_per_work_unit` = **one** row per department scope (not one row per WU).

**Seeds — idempotent (adminV2 v0)**

Use upsert / `ON CONFLICT` aligned with unique indexes so re-runs are safe.

**Required seed `metric_key` values:**
- `org.structure.departments_count` — `surface=workspace`, scope nulls
- `org.structure.work_units_count` — `surface=workspace`, scope nulls

- `dept.wu_queue.total_per_work_unit` — `surface=department`, **`department_id` set per target dept** (document fixture
  org / dept ids for local dev)

**Optional / deferred in seeds (omit unless product expands Card 2):**
- `wu.queue.selected_tab_count`

Set sort/display order in seeds to match today’s left-to-right read (structure → pipeline → dept facet).
