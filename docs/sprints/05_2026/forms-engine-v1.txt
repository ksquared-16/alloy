## Approved architecture decisions

The following are **locked for V1** unless an explicit architecture review reopens them:

- **Dedicated versioned form schemas** stored on `form_definition_versions` (`schema_json`); **`field_definitions` is not** the default form schema.
- **`form_submissions.payload` JSONB** is the **source of truth** for captured answers.
- **No automatic writes** of submission answers to **`field_values`** (optional **promoted-field** mappings deferred post-V1 unless explicitly rescoped).
- **Generated PDFs** are normal **`documents`** rows (Storage + metadata); **no second documents system**.
- **`form_submission_documents`** junction links submissions to **`documents`** (e.g. `generated_pdf`, `signature_asset`).
- **`documents.entity_type`** uses singular **`customer_member`** for child-scoped files (aligned with upload canonicalization in **`web/app/api/admin/documents/upload/route.ts`**).
- **Public forms** resolve **`org_id`** via **`form_public_links`** + **`token_hash`** — **not** `ALLOY_PUBLIC_ORG_ID`.
- **Published** `form_definition_versions` are **immutable**; changes require a **new** version row.
- **Workflow events (snake_case):** **`form_submitted`**, **`form_signed`**, **`form_document_generated`**; **`workflow_events.entity_type`** for these events is **`form_submissions`**.
- **Signatures:** typed + drawn supported structurally (**`form_submission_signatures`** + optional **`documents`** for drawn assets); **DocuSign / external providers not implemented in V1** beyond nullable future-ready columns.
- **One shared person-first intake helper** for CRM side effects from public (and optionally staff) submit — **no new CRM intake model** (reuse persons, customers, `customer_persons`, `customer_members`, opportunities, `opportunity_*` joins).

**Implementation note:** `customer_member` is already valid on **document upload** canonicalization; **admin picker / `V1_DOCUMENT_ENTITY_VALUES`** must be extended later per **`web/lib/admin/v1DocumentEntities.ts`** and **`/api/admin/documents/entity-options`**.

## 1. Sprint title

**Forms Engine V1 — Foundational enrollment, compliance, intake, signatures, and PDF artifacts**

---

## 2. Purpose / north star

Alloy needs a **single, coherent Forms Engine** that supports childcare **enrollment**, **compliance**, **web intake**, **signatures**, **generated PDFs**, and future **financial / subsidy** workflows—without fragmenting CRM, documents, or workflow semantics.

The north star is: **structured form submissions are the durable source of truth**; **PDFs are reproducible compliance artifacts** derived from those submissions and integrated with the **existing documents system**.

---

## 3. Core doctrine

- **Structured form submissions are the source of truth.** All business logic, reporting, and CRM linkage should reason over structured data (validated payloads and/or normalized storage), not over PDF bytes.
- **PDFs are generated compliance artifacts, not the source of truth.** Official-looking outputs must be **reproducible** from versioned form definitions and submission data.
- **Do not create a second documents system.** Generated PDFs must **integrate with the existing documents system** (storage, metadata, permissions, UI patterns).
- **Do not create a generic drag-and-drop form builder.** Prefer versioned schemas, templates, and controlled configuration over an open-ended builder abstraction.
- **Do not create a second custom field system unless the audit proves it is necessary.** Prefer reuse of existing field definition/value patterns where they fit; only introduce parallel systems with explicit audit justification.
- **Do not create a second CRM intake model.** Reuse **persons**, **customers**, **customer_persons**, **customer_members**, and **opportunities**. **Customer members are the canonical child records.**
- **Web intake must create CRM records through existing person-first CRM helpers where possible** (consistency, fewer code paths, fewer security footguns).
- **Forms must be versioned.** Submissions must bind to the definition version used at capture time so compliance and audits hold.
- **State-required forms** must preserve **exact required fields** and be **reproducible as official PDFs** (layout and field fidelity per regulatory needs).
- **Center-level forms** can be **more flexible and config-driven** while still versioned and validated.
- **Signatures in V1:** support capture, storage contract, and workflow hooks; **external signature providers** are **designed for**, not fully implemented in V1.
- **PDF generation via a mapping layer**, not a general-purpose PDF engine inside the product core. Treat mapping as a contract between structured data and document output.
- **Do not conflict with the existing workflow/event system.** Emit **`form_submitted`**, **`form_signed`**, and **`form_document_generated`** (after design lock) with explicit payload contracts; **`entity_type`** for these events is **`form_submissions`**.
- **Public iframe / web forms are critical for lead capture** and must be first-class in routing, security, and abuse controls.
- **No implementation begins until Cards 0, 0.5, 1, and 1.5 are complete and reviewed.**

---

## 4. What Forms Engine V1 is

- A **versioned** system for defining forms, capturing **validated structured submissions**, linking them to **existing CRM entities**, and producing **compliance PDFs** through a **mapping layer**.
- A path for **public web intake** that can **safely** create or update **person / customer / customer_member / opportunity** records using **shared CRM helpers**.
- A foundation for **signatures** (internal representation + lifecycle) with a **pluggable** path to external providers later.
- An integration surface for **workflow/events** that **extends** current patterns rather than replacing them.

---

## 5. What it is NOT

- Not a second **documents** product or DMS.
- Not a **generic form builder** (drag/drop, arbitrary page builders, marketing “canvas” forms).
- Not a parallel **custom fields** platform unless **proven necessary** by audit.
- Not a new **intake/lead** data model separate from **opportunities** and related entities.
- Not a **full PDF composition engine** as the core abstraction (no open-ended WYSIWYG PDF designer in V1).
- Not a replacement for the **workflow/event** framework.

---

## 6. State-required forms vs center-level forms

| Dimension | State-required forms | Center-level forms |
|-----------|----------------------|--------------------|
| **Regulatory fidelity** | Must preserve **exact required fields**; official PDF reproduction is a hard requirement. | More room for **config-driven** fields and flows; still validated and versioned. |
| **Change control** | Strong **versioning**, audit trail, and controlled publishing. | Versioning + center-scoped configuration where appropriate. |
| **PDF output** | Must map to **official templates** / layouts (mapping layer drives fidelity). | PDFs may be simpler or internal; still via **mapping**, not ad hoc one-offs. |
| **Flexibility** | Low (by design). | Higher (within guardrails). |

---

## 7. Existing systems that must be reused

- **Documents system:** storage, linkage, permissions, existing UI/listing patterns—**generated PDFs land here**.
- **Entity model:** `persons`, `customers`, `customer_persons`, **customer_members (canonical children)**, `opportunities`.
- **CRM intake helpers:** person-first creation/update flows for intake (no parallel “lead object” unless audit forces a minimal extension—default is **no**).
- **Config system:** existing patterns for environment/center/feature configuration where applicable.
- **Field system (conditional):** `field_definitions`, `field_values`, `field_section_definitions`, `record_layouts`—**reuse vs parallel schema** is an explicit Card 0 / 0.5 decision.
- **Workflow / events:** extend with **approved** events only; no second orchestration layer.

---

## 8. Explicit anti-drift / anti-redundancy rules

- **One documents system of record** for stored files and metadata; Forms Engine **links** into it.
- **One CRM entity path** for intake: prefer **existing helpers** and tables; avoid “forms-specific” copies of person/child/opportunity state.
- **One field/custom metadata strategy:** either **reuse** field_definitions/values or **isolate** form payloads with a documented reason—**not both** without boundaries.
- **One PDF strategy:** **mapping contract** + template assets; avoid embedding unconstrained PDF logic across services.
- **One event vocabulary** for forms: names and payloads **approved** before build; no ad hoc `console.log`-style event sprawl.
- **Version everything that affects compliance:** definitions, mappings, and submission binding.

---

## 9. Success criteria

- **Structured submissions** are authoritative for operational and compliance queries; PDFs can be **regenerated** from submission + version + mapping.
- **No second documents system**; staff can find generated PDFs **alongside** existing document UX.
- **Public iframe intake** works for lead capture with **clear security model** (abuse, rate limits, auth where needed, PII handling).
- **Entity linking** uses **customer_members** as canonical child records and ties cleanly to **opportunities** where required.
- **State form path** demonstrates **field fidelity** and **reproducible** official PDF output for at least one concrete example (see Card 10 seed).
- **Signatures** have a **defined contract** (what is stored, what is shown, audit metadata) even if external providers are stubbed.
- **Workflow integration** does not fork the existing system; **approved** events are emitted at the right lifecycle points.
- **Tests and documentation** cover the above; **architecture freeze** respected through build.

## 13. Detailed Card 0.5: Architecture Risk Review

**Objective:** Resolve open decisions and record **risks / mitigations** before data model lock.

**Required open design questions (must be addressed in the Card 0.5 write-up):**

1. **Schema strategy:** Should form schemas **reuse** `field_definitions` (and related structures) or **remain separate** with explicit boundaries?  
2. **Submission storage:** Should form submissions **write to** `field_values`, **only** store payload JSON (validated), or a **hybrid**—and why?  
3. **PDF ↔ documents:** How should **generated PDFs** **link** to the existing **documents** model (FKs, metadata, naming, idempotency, regeneration)?

5. **Signatures:** How should **signatures** be **stored** (cryptographic hash, image, provider ref, audit fields)? What is **not** stored?  
6. **Events:** What **events** should be emitted (`form_submitted`, `form_signed`, `form_document_generated`, others)? Payload shape? Ordering guarantees?  
7. **Approval gate:** What items need **explicit approval** before any Phase 3 build (schema boundaries, RLS, public surface, PDF contract)?

**Output:** decision log (with options, pick, rationale), residual risks, and **conditions** for entering Card 1.

## Appendix C — Card 1: Final data model (completed output)

*Design only; no migrations executed.*

### C.1 Tables

1. **`form_definitions`** — Logical form per org: `key`, `name`, `kind` (`state` \| `center`), `is_active`, `metadata`; **`UNIQUE (org_id, key)`**.  
2. **`form_definition_versions`** — `form_definition_id`, **`org_id`** (denorm for RLS), **`version_number`**, **`status`** (`draft` \| `published` \| `archived`), **`schema_json`**, **`pdf_mapping_json`**, `published_at`, `published_by_user_id`, `metadata`; **`UNIQUE (form_definition_id, version_number)`**; **published rows immutable** (app + optional trigger).  
3. **`form_submissions`** — `form_definition_id`, **`form_definition_version_id`**, **`status`** (`draft` \| `submitted` \| `void`), **`payload` JSONB**, nullable FKs: **`person_id`, `customer_id`, `customer_member_id`, `opportunity_id`**, **`created_via_public_link_id`**; `submitted_at`, `metadata`, audit user ids; **no `customer_persons` FK** (implied by person + customer + helper).  
4. **`form_submission_documents`** — **`form_submission_id`**, **`document_id`**, **`role`** (`generated_pdf` \| `signature_asset` \| …), `sort_order`, `metadata`; **`UNIQUE (form_submission_id, document_id)`**.  
5. **`form_public_links`** — **`token_hash`** (unique), optional `token_prefix`, `form_definition_id`, **`pinned_form_definition_version_id`**, `is_active`, `expires_at`, **`allowed_embed_origins`**, **`rate_limit_profile`**, `metadata`, `last_used_at`.  
6. **`form_submission_signatures`** — `form_submission_id`, **`field_id`**, **`instance_key`** (default `''` for repeatables), **`signature_kind`** (`typed` \| `drawn`), `typed_full_name`, **`drawn_asset_document_id`**, `signer_acknowledged_at`, `signer_ip_hash`, `metadata`, **`external_provider`**, **`external_envelope_id`** (nullable V1); **`UNIQUE (form_submission_id, field_id, instance_key)`**.  

**Deferred V1 tables:** `form_promoted_field_mappings`, `form_pdf_mappings` (use **`pdf_mapping_json`** on version only).

### C.2 Entity linking

- Explicit nullable FKs on **`form_submissions`**; **`customer_persons`** maintained by intake helper, not a submission FK.

### C.3 Versioning

- **Logical form** = `form_definitions`; **immutable published** rows in `form_definition_versions`; **submissions** always reference **`form_definition_version_id`**; edits = **new version**.

### C.4 `schema_json` contract (V1 strict)

- Top-level: **`schema_version`**, `title`, **`sections`**, **`fields`** with closed **`type`** set, **`option_set_key`**, **`visibility`**, **`group`** (repeatable), **`signature`**, **`entity_hint`**, optional **`pdf.slot_key`**.  
- **Not** a record-layout clone of `field_definitions`.

### C.5 `payload` contract

- **`values`**, **`groups`** (array of `instance_id` + `values`), optional **`signatures`** mirror, **`meta`** timestamps; **submit** freezes **`payload`**; **authoritative signatures** in **`form_submission_signatures`** (+ documents for drawn).

### C.6 Documents linkage

- PDF/signature assets: Upload bytes → **`documents`** (`entity_type`/`entity_id` per policy — **`customer_member`** for child-specific) → **`form_submission_documents`**. **`template_key`**, **`generated_from_document_id`**, **`metadata.idempotency_key`** recommended.

### C.7 Public links

- **Plaintext token** → hash → row → **`org_id`** + resolved **version** (pinned or latest **published**).

### C.8 RLS (high level)

- Org-scoped tenant tables; **no** anonymous writes; **public** writes only via Route Handlers + **service role** after token verify.

### C.9 Event payload IDs (references only)

- Include **`form_submission_id`**, **`form_definition_id`**, **`form_definition_version_id`**, **`org_id`**, entity FKs, **`document_id`** when applicable, **`created_via_public_link_id`**.

### C.10 Migration order (future)

`form_definitions` → `form_definition_versions` → `form_public_links` → `form_submissions` → `form_submission_documents` → `form_submission_signatures`; align **`org_id`** denorm with triggers; extend **document entity allowlist** + **entity-options** for **`customer_member`**.

## Appendix D — Card 1.5: API + rendering design (completed output)

*Design only; aligns with Alloy patterns verified in codebase (`getAdminContextCached`, `createAdminClient`, `createServiceRoleClient`, `/api/admin/**`, `/api/public/**`, `documents` canonical types).*

### D.1 Admin APIs (`/api/admin/forms/**`)

- **Auth:** `getAdminContextCached` + `adminContextFailureResponse`; **`getAdminAccessContextCached`** where submission listing needs dept/site scope.  
- **DB:** `createAdminClient()` post-gate.  
- **Mutations** on definitions/versions/publish/links:** **`ctx.role === 'admin'`** (match documents upload strictness).  
- **Routes (summary):** list/create **`/api/admin/forms`**; **`/[definitionId]`** GET/PATCH; **`/[definitionId]/versions`** GET/POST; **`/[definitionId]/versions/[versionId]`** GET/PATCH (draft only); **`/publish`**, **`/archive`**; submissions **`/api/admin/forms/submissions`** GET, **`/[submissionId]`** GET, **`/[definitionId]/submissions`** POST draft, **`/[submissionId]`** PATCH draft, **`/[submissionId]/submit`** POST; **`/[submissionId]/generate-document`** POST; **public-links** CRUD under **`/[definitionId]/public-links`** and **`/public-links/[linkId]`** PATCH.  
- **Admin response convention:** errors **`{ error, code? }`**; success = resource JSON or paged list.

### D.2 Public APIs (`/api/public/forms/**`)

- **`createServiceRoleClient()`** only inside handlers.  
- **Token:** header **`Authorization: Bearer`** or **`X-Form-Link-Token`** (avoid querystring logging).  
- **Routes:** **`POST …/bootstrap`** (token → schema + version + link meta, **omit raw `org_id` to client by default**); **`POST …/submissions`** create draft; **`PATCH …/submissions/[id]`**; **`POST …/submit`**; **`POST …/assets`** multipart (drawn/file_ref) mirroring **`specialty-quote-start`**.  
- **Public response convention:** **`{ ok: true \| false, message?, code?, … }`** (book-v2 style for writes).

### D.3 Validation

- Server module compiles **`schema_json`** → **draft** vs **submit** validators; **`option_set`** resolution per `org_id`; visibility before required; groups + signatures; lives under e.g. **`web/lib/forms/**`** (implementation).

### D.4 Renderers

- **Schema-driven list** — no drag/drop builder; staff + iframe/mobile share field order from **`schema_json`**; draft vs submitted modes; typed + drawn + file_ref flows.

### D.5 Person-first intake helper (contract)

- **Inputs:** `org_id`, validated `payload`, `schema_json`, mode flags; **Outputs:** `person_id`, `customer_id`, `customer_member_id?`, `opportunity_id?`.  
- **Steps:** find/create **person** → **customer** + **`customer_persons`** → **member** / **opportunity** / **`opportunity_customer_members`** / **`opportunity_persons`** as required; **no contacts** unless explicit legacy flag.  
- **Idempotency:** keyed on person identifiers + submission lifecycle (single **submit** transition).

### D.6 PDF generation

- **Admin** `POST …/generate-document`; optional auto on submit via version metadata flag.  
- **`pdf_mapping_json`:** e.g. `{ engine, template_key, slots: { slot: { path } } }`; service **`buildPdfFromSubmission` → Buffer** (implementation); **idempotency** via metadata hash; **regenerate** = new `documents` row + **`generated_from_document_id`**.

### D.7 Signatures

- **Typed:** rows in **`form_submission_signatures`**.  
- **Drawn:** **`documents`** + **`form_submission_documents`** (`signature_asset`) + **`drawn_asset_document_id`**.  
- **`form_signed`** event once per submit if signatures present (V1 default).

### D.8 Workflow / events

- **`form_submitted`** after successful submit commit; **`form_signed`** same request if applicable; **`form_document_generated`** after PDF row + junction.  
- **Emit after** successful DB writes; **log** on `emitEvent` failure (align **`document_uploaded`** tolerance).  
- Register types in **`workflowVocab`** when implementing.

### D.9 Security / abuse

- **Hash-only** token storage; constant-time compare; **rate limit** by token hash + IP; **origin** check vs **`allowed_embed_origins`**; **hashed IP** in metadata; **no** client service role.
