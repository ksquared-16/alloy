CARD 0.5 — Prerequisites / Decisions Gate

Purpose:
Before implementation, explicitly define decisions and prerequisites so work is not executed blindly.

1. Provider strategy
- Existing Twilio is one-off / Alloy Services only.
- Do not assume global Twilio credentials are the future.
- Tenant-specific provider configuration is required.
- SMS V1 may support Twilio, but only through org-scoped provider accounts (not deployment-wide secrets as the sole model).
- Email provider is undecided for V1; evaluate simple transactional options such as Resend, Postmark, or SendGrid in Card 1 and record the choice here once approved.

2. Canonical storage decision
- Existing public.messages lacks org_id and is not sufficient as-is for multi-tenant communications.
- Decision required: evolve public.messages (e.g., add org_id, threading, tighten RLS) versus introduce a new communications schema/table family.
- Duplicate source-of-truth between messages and messages_outbox must be resolved; define one canonical store (and demote or retire the other to audit/replay-only if needed).

3. Tenant isolation
- All messages must be org-scoped at rest and in APIs.
- Inbound messages must resolve org_id deterministically (explicit routing or verified mapping—not guesswork across tenants).
- No cross-tenant sends, reads, or provider leakage (credentials, webhook handling, queues, logs).

4. Event / action model
- Messages must emit canonical events (queued, sent, received, failed, read as applicable).
- Send message is a system/admin action compatible with Alloy actions/workflows; design must tie into that model.
- Do not build a parallel activity system.
- Communications events feed workflow_events and the activity timeline (same stream consumers use today).

5. Permissions
- Define V1 rule for who may send versus read versus configure providers (org roles / explicit permission keys).
- Note a future capability/scope model if V1 stays coarse (e.g., department/work-unit scoped messaging later).
- Daily send caps, rate limits, and abuse controls are future; capture as non-goals or follow-ups unless explicitly in scope.

6. Future north star
- Photo/media upload.
- Media assigned to child/person/entity.
- AI-drafted messages tied to media/context.
- Human approval step before send.
- Message sent; events/workflows/activity updated accordingly.

7. Explicit stop condition
- After Card 1 (Communications Design / Architecture Proposal), stop again for review.
- Do not proceed to implementation Cards 2+ until Card 0.5 prerequisites and Card 1 design outputs are explicitly approved AND CARD 1.5 (Final Decisions Before Implementation) is reviewed and explicitly approved.

CARD 1.5 — Final Decisions Before Implementation

Record decisions and open confirmations here. Do not proceed to implementation Cards 2+ until this card is reviewed and explicitly approved.

1. Canonical storage
Decision: Use new communication_* tables as the future canonical model.
Legacy public.messages and messages_outbox are compatibility/migration paths only.

2. SMS provider
Decision: V1 supports Twilio through org-scoped communication_provider_bindings.
Do not use global TWILIO_* env vars for tenant communications except legacy/Alloy Services paths.

3. Email provider
Decision needed before implementation:
Recommend Resend for V1 unless we choose Postmark.
Do not implement SendGrid unless explicitly approved.

4. Inbound routing
Decision: V1 inbound SMS must route deterministically by binding_id or verified To number → provider binding.
Do not rely on phone/contact heuristics to infer org.

5. Threading
Decision: V1 thread should resolve by:
org_id + primary_entity_type + primary_entity_id + channel + recipient identity
unless explicitly creating a new thread.
Do not create random new threads for every message.

6. Event naming
Decision needed:
Use message_* event names if continuing existing semantics.
Alternative: communication_message_* for clearer namespace.
Pick one before migration.

7. Provider secret storage
Decision needed before code:
Define whether V1 stores secret_ref only, and where actual secrets live:
- environment-managed lookup
- Supabase Vault
- another secret manager
Do not store provider API keys or auth tokens in plaintext jsonb.

8. Permissions
Decision: V1 may start with admin/ops + communications.send/read/configure checks.
Do not build full capability/scope system yet, but leave hooks.

9. GHL
Decision: GHL send_conversation_sms remains outside tenant communications V1 unless routed through the same communication provider abstraction and canonical message store.

10. Sender identity model
V1 must be designed to support sender identity resolution at multiple scopes:
1. Org-level default sender
2. Location-level sender
3. User-level connected sender

Resolution order:
user-level sender > location-level sender > org-level sender

Implementation may start with org-level or location-level sending, but the schema and provider abstraction must not block user-level Gmail/Outlook-style sending later.

User-connected email is not required for the first implementation slice, but it is a required future direction.

11. Implementation stop condition
Do not proceed to implementation Cards 2+ until this Card 1.5 is reviewed and explicitly approved AND CARD 1.6 — Decision Lock / Build Readiness is explicitly approved (see CARD 1.6 implementation gate).

Card 24 — Twilio Inbound Hardening

Goal:
Secure inbound SMS handling before production use.

Scope:
- Implement Twilio signature validation
- Add kill switch for inbound endpoint
- Preserve legacy compatibility
- Do NOT change outbound SMS

IMPLEMENTATION (2026-05 sprint — shipped)

- **Routes:** `POST /sms/inbound` and `POST /sms/inbound/{binding_id}` (`backend/app/routes/sms_inbound.py`).
- **Signature:** `X-Twilio-Signature` validated with `twilio.request_validator.RequestValidator` (`backend/app/services/twilio_inbound_signature.py`). **Auth token resolution:** for the binding route, load `communication_provider_bindings` by `binding_id`; if `secret_ref` is `env:VAR`, use that env value; if `legacy_global_twilio` or `unconfigured`/missing resolved secret, fall back to process **`TWILIO_AUTH_TOKEN`** (same as legacy global Twilio). For the legacy route (no binding), use **`TWILIO_AUTH_TOKEN`** only. If no auth token is available, inbound returns **403** (no legacy insert, no canonical communication rows, no success-path workflow events).
- **Validation URL:** Twilio signs the full webhook URL. By default the app uses `str(request.url)` (scheme + host + path + query). If the API sits behind a proxy and the public URL differs, set **`COMMUNICATIONS_TWILIO_INBOUND_VALIDATION_BASE_URL`** to the public origin only (e.g. `https://api.yourdomain.com`); validation then uses that base + request path + query. Must match the URL configured in Twilio Console for the webhook.
- **Kill switch:** **`COMMUNICATIONS_SMS_INBOUND_ENABLED`** — when set to `false`, `0`, `no`, or `off` (case-insensitive), inbound returns **200** with empty TwiML `<Response></Response>` and performs **no** database writes and **no** workflow event emission. When unset or any other value, inbound is **enabled** (backward compatible with deployments that did not set the flag).
- **Invalid signature / missing token:** **403**; no `public.messages` insert, no `communication_*` persistence, no `message_received` (or other) success events from this path.
- **Logging:** Structured lines with prefix `sms_inbound_guard` and events `inbound_disabled`, `signature_invalid` (reasons `no_auth_token`, `bad_or_missing_signature`), `validation_ok`. No full bodies; binding ids **masked**; no secrets.
- **Tests:** `backend/tests/test_twilio_inbound_signature.py` (unittest). Run from `backend/`: `python -m unittest discover -s tests -p 'test_*.py'` (requires `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` in env for `settings` import, or use the project `.env`).
- **Explicitly unchanged:** Outbound SMS, Resend/email, KPI code paths, `COMMUNICATIONS_DUAL_WRITE`, canonical threading semantics beyond validation order-of-operations.

**Inbound canonical persistence (legacy `POST /sms/inbound`):** After signature validation, the handler loads **all active** SMS bindings whose **`inbound_to_e164`** equals **`normalize_phone(Twilio To)`** via **`find_sms_bindings_by_inbound_to`** (`binding_resolver.py`). **Exactly one** match → **`persist_inbound_communication_sms`** (`communication_inbound.py`) for that org/binding **before** legacy **`public.messages`** insert. **Zero** matches → **`sms_inbound: canonical_skip no_binding`** (masked `to_tail`). **Multiple** matches → **`canonical_skip ambiguous_destination_binding`** — legacy insert only (no guessed org). Explicit **`POST /sms/inbound/{binding_id}`** unchanged. Person resolution: one org-scoped **`persons`** row by phone → anchor **`persons`**; zero → **`communications_unknown`** + surrogate metadata **`unknown_sender`**; ≥2 → surrogate **`ambiguous_sender`** + **`candidate_person_ids`** (no pick-one). Logs: **`canonical_ok`** (message id tail + masked binding); **`canonical_persist noop`** if PostgREST insert fails silently.

CARD 22 — Delivery Truth Model — DESIGN DELIVERABLES

Purpose:
One canonical vocabulary for “where is this message in its delivery lifecycle?” across **email (Resend)**, **SMS (Twilio)**, and **in-app**, without pretending provider-specific tokens mean more than they do.

1. Canonical states (operator-facing vocabulary; internal storage may alias)

| Canonical state | Meaning |
|-----------------|--------|
| **queued** | Alloy has accepted the outbound intent; message not yet handed to provider (or still in local/worker queue). Maps to today’s `communication_messages.status = queued` while worker pending. |
| **sent_to_provider** | Alloy’s worker is dispatching or has invoked the provider client; provider may still be accepting. Use when Twilio API returns a Message **SID** but Twilio **message.status** is still `queued` / `accepted` / similar — i.e. **handoff to carrier not finished from Alloy’s perspective**. (Optional subdistinction: may stay internal; not required in UI if noisy.) |
| **provider_accepted** | Provider **accepted the request** and gave a durable id (Resend `id`, Twilio `sid`). **Does not** mean the recipient’s mailbox or handset received the content. |
| **delivered** | **Confirmed** end-to-end delivery to recipient **per provider-trusted signal** (email: delivery webhook or equivalent; SMS: Twilio **delivered** status or delivery receipt webhook). **Not** the same as “API call succeeded.” |
| **failed** | Terminal failure before or during provider send (HTTP error, validation, missing binding, Twilio error). Maps to today’s `communication_messages.status = failed` + `error`. |
| **bounced** | Provider accepted send path but later reports **non-delivery to recipient** (email bounce). Distinct from **failed** (which is typically synchronous send-time). May require provider webhook + stored bounce detail. |
| **inbound_received** | Inbound message persisted (SMS or future inbound email). Not an outbound state; used for thread rows that are **inbound** direction. Aligns with inbound persistence + `message_received` style events. |

2. Semantics (non-negotiable clarifications)

- **Resend:** A successful `POST /emails` returns an **`id`**. That id means **provider_accepted** in the canonical model — **not** **delivered**. True delivery requires Resend **webhooks** (delivered, bounced, etc.) or equivalent; until then, UI should allow **“delivery not confirmed.”**
- **Twilio outbound:** A successful REST `messages.create` yields a **SID** and often an initial **`status`** of `queued` (or similar). That is **not** handset delivery. **`delivered`** in the canonical model must only be set when **`status`** (or webhook) indicates **delivered** (or documented equivalent). **Do not** label Alloy message rows **delivered** based solely on send API success.
- **Current implementation gap (SMS):** `communication_message_sender` patches outbound SMS to `status: "sent"` and emits **`workflow_events` `message_delivered` with `extra.note: optimistic-after-send`**. That workflow event name is **misleading** relative to canonical **delivered**. Operators must be told this is **not** confirmed delivery until Twilio callbacks/webhooks back it (see Card 23). Persistence does not currently store a separate “optimistic delivery” vs “confirmed delivery” flag on `communication_messages` — **schema / event naming gap**.

3. Mapping: provider signals → canonical (implementation reference for a future card)

- **Resend:** HTTP 200 + body `id` → **provider_accepted** (and enqueue webhook subscription for delivered/bounced later). HTTP non-2xx / exception before id → **failed**.
- **Twilio REST create:** return `sid` + Twilio `status`:
  - `queued`, `accepted`, `sending`, … → **sent_to_provider** or **provider_accepted** (product choice: prefer **provider_accepted** once `sid` exists; use **sent_to_provider** only if we need finer distinction before sid).
  - `delivered` (when Twilio reports it on the resource or via webhook) → **delivered**.
  - `failed`, `undelivered` → **failed** (or terminal non-delivery; align with SMS error taxonomy).
- **In-app:** internal **queued** until written → **delivered** when persisted to thread (no third-party); or treat as **provider_accepted** instantaneously if we consider Alloy the provider — product call: prefer **delivered** for in-app once stored, since there is no external mailbox.

4. Schema / storage gaps (proposals only — no migrations in this batch)

- **`communication_messages.status`** today behaves like a coarse enum (**queued** / **sent** / **failed**). It does **not** distinguish **provider_accepted** vs **delivered** vs **bounced**. **Proposal:** either (a) extend allowed values + migration, or (b) add **`delivery_substate`** or **`canonical_delivery_state`** JSON/column, plus **`provider_last_event_at`**.
- **Provider id:** `provider_message_id` already stores Resend id / Twilio sid — good anchor for webhook correlation.
- **Metadata:** Store Resend/Twilio **raw last status** (or webhook payload tail) in **`metadata`** for debugging — **proposal** only.
- **Workflow events:** Consider renaming or adding event types so **`message_delivered`** is only emitted when canonical **delivered** is true; keep **optimistic** SMS under **`message_sent`** + explicit **`delivery_unconfirmed`** or metadata on payload **until webhooks exist** — **proposal** only; must preserve audit trail when changing names (append-only / new types).

CARD 23 — Operator Truth UX — DESIGN DELIVERABLES

Goal:
Operators never infer “they got it” from **provider id** or **“sent”** alone.

1. Truth tiers (for copy and badge styling)

| Tier | Meaning for operators |
|------|------------------------|
| **Confirmed (safe to assert receipt path)** | Only **delivered** (canonical) backed by provider-trusted signal. Rare for email without webhooks. |
| **Accepted by provider (not receipt)** | Resend id / Twilio sid obtained — **“Sent to provider”** — **delivery not confirmed**. |
| **In flight (Alloy)** | **queued** / worker pending — **“Sending…”** or **“Queued”**. |
| **Not OK** | **failed**, **bounced** — show reason when `error` / bounce detail exists. |

2. Per canonical state — drawer display (concise copy; final strings TBD in UX pass)

| Canonical state | Primary label (suggestion) | Secondary / tooltip |
|-----------------|----------------------------|----------------------|
| **queued** | **Queued** | “Waiting to send.” |
| **sent_to_provider** | **Sending…** or **Handed to carrier** | “Provider is processing.” |
| **provider_accepted** | **Sent to provider** | **“Delivery not confirmed.”** Do **not** use “Delivered.” |
| **delivered** | **Delivered** | Optional timestamp; only if webhook/status proves delivery. |
| **failed** | **Failed** | Show **`error`** snippet when present; link to retry policy (future). |
| **bounced** | **Bounced** | “Provider could not deliver (e.g. invalid address).” |
| **inbound_received** | **Received** | Inbound row; separate from outbound pipeline. |

3. Email (Resend) — operator messaging

- After successful enqueue/API id: show **“Sent to provider”** + **“Delivery not confirmed”** (subtitle or muted line).
- Never equate Resend **id** with inbox delivery.

4. SMS (Twilio) — operator messaging

- After Twilio SID: **“Sent to provider”** + **“Delivery not confirmed”** until Twilio **delivered** (or equivalent).
- **Explicitly call out today’s gap:** the system may emit **`message_delivered`** workflow events **optimistically** for SMS (`optimistic-after-send` in backend) — **drawer must not show plain “Delivered”** for that path until persistence reflects canonical **delivered** or copy overrides to honest wording.

5. Failed / bounced

- **failed:** Red or warning accent; show truncated **`error`** from row; avoid blame-specific language in default copy.
- **bounced:** Distinct from **failed** (post-acceptance); use for email bounces when webhook exists.

6. Safe vs “not confirmed” summary

- **Safe to treat as confirmed delivery:** canonical **delivered** only (with provider evidence).
- **Must show “delivery not confirmed”:** **provider_accepted**, **sent_to_provider**, and any **optimistic** delivery signal (current SMS workflow event **until** reconciled).
- **Inbound** rows: **Received** — separate pipeline; do not mix with outbound delivery truth.
