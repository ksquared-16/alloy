## Why a migration is needed

`documents.status` has no check constraint, so `archived` could be written without one. Doing so would be unsafe: six
database functions decide availability from a hard-coded list (`deleted, quarantined, restricted, superseded`) and would
keep treating an archived document as available. It could then still be filed, filed onto, given a version, reviewed or
have its dates changed. The TypeScript side already treats `archived` as unavailable (`documentAvailability.ts`,
the requirement evaluator's `NEVER_EVIDENCE`). That is inert until a database can hold the status.

## What it contains

1. **The same six functions, with `'archived'` added to the unavailable list (7 occurrences), otherwise byte-for-byte the
   latest definition.** Generated by extracting each function's latest `CREATE OR REPLACE` from `supabase/migrations` in
   order. `document_add_version`, `document_filing_existing_of_type`, `document_file`, `document_file_as_version` (×2),
   `document_review_version`, `document_set_version_validity`. Privileges survive `CREATE OR REPLACE`.
2. **`document_archive(org, document, reason, archive_key, actor, audit_event_id)`**, the only writer of `archived`. It
   locks the row and needs a reason. A retry with the same key answers `replay`. It refuses a document that is already
   unavailable or archived under another key. It records `metadata.archive` (key, reason, previous status, actor, audit
   event, time). Nothing is deleted.
3. **`document_unarchive(...)`**, staff-only reversal to the previous status. It requires a user actor, and no `/api/v1`
   route calls it. Staff reach it through `POST /api/admin/documents/[id]/restore` (`01141ac30`). That route needs
   `documents.write`, read admission, scope and sensitivity, an archived document and a written reason, and it is
   audited `document_restored` first. Staff find archived documents in the library's collapsed **Archived** section
   (`GET /api/admin/documents/archived`).
4. Service-role-only grants and a self-verification block.

## Proof so far

- **Local, synthetic:** `documentsLifecycleSurface.test.ts`. The operation answers 503 `archive_unavailable` while the
  function is absent and writes no status. With the function's contract present, it archives once, the document leaves
  `listDocuments`, a retry replays, another key gets 404, and no version or object is removed. The D6 evaluator test
  shows `archived` is never evidence.
- **Not proven:** the SQL itself. On 2026-11-03 a syntax check inside a rolled-back transaction on the shared
  `alloy-cert` stack failed before reaching it: `relation "public.document_subjects" does not exist`. The stack's ledger
  stops at `20261210090000` and has none of the Documents D2–D8 functions, so no isolated database exists yet where this
  migration (or application-as-actor filing) can be exercised. Nothing remained after the rollback.
